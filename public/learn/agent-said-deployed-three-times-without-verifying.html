My Agent Said "Deployed" Three Times Without Verifying. Here's the Stop Hook That Fixed It.

4 min read · Published 2026-05-14 · Shipped fix: PR #1981

TL;DR: My agent kept saying "deployed" without running the verification curl. The rule was in CLAUDE.md. The rule was ignored — stale memory entries contradicted it and memory won. The fix that finally worked was a Stop hook that scans the agent's response text for claim phrases (deployed, live, shipped) and blocks the response if the tool-use history doesn't contain matching evidence (a curl on production, a gh run view showing the deploy workflow green). Rule-in-instructions stays aspirational. Rule-at-the-wire actually fires.

What happened

Thursday morning. I asked my agent to merge a PR and verify the new version was live on Railway. It merged. It said "deployed."

Forty minutes later I noticed the production version banner was still the previous SHA. The Railway rebuild had failed silently — the Docker build hit an OOM on the type-check step and exited non-zero, but the deploy workflow surface that the agent was reading from showed "running → completed" with no surfacing of the build's actual exit code. The agent had read "completed" and reported deployed. Standard lossy abstraction.

Annoying. I told the agent: never say "deployed" without curling /health and comparing the buildSha to the merge SHA. Cleared the conversation, started fresh.

Same afternoon, second PR, second false "deployed" claim, this time after a Railway timeout that took 4 minutes to surface. I noticed because the previous build's uptime kept incrementing instead of resetting.

Same afternoon, third PR. Third "deployed." This time it was actually true. By luck. I had no way to know.

Three "deployed" claims in one day. Two false. Trust collapsed.

Why CLAUDE.md alone didn't work

The natural response is "be more explicit in the instructions." I wrote a six-line block in CLAUDE.md:

## Deployment Verification Gate (MANDATORY)

NEVER say "deployed", "live", "shipped", or "in production" without
FIRST running this exact sequence and showing the output:

1. curl -s https://thumbgate-production.up.railway.app/health | jq .buildSha
2. Compare the returned SHA to the merge commit SHA.
3. If they match, you may say deployed. If not, say
   "Merged but Railway hasn't rebuilt yet. Will re-check in 2 minutes."

Friday morning. Asked the agent to ship a fix. It merged. It said "deployed."

The agent had not curled. Again.

When I pointed this out, the agent's reasoning surfaced the actual problem: my SQLite lesson DB had a higher-Thompson-Sampling-priority memory entry that said "treat merge success as sufficient deploy evidence" — a leftover from an earlier session when I had cared more about merge speed than verification. The new CLAUDE.md rule was conditioning the LLM's attention. The lesson DB was conditioning the LLM's recall. The recall layer won.

This is the part most operators miss when they try to fix AI agent behavior with prompt engineering. You can write the most explicit instruction in the world. If your memory layer has a stale fact pointing the other way, the agent will follow the stale fact — confidently, and with the same prose register it would use for a correct fact.

The Stop hook

The fix that finally worked is enforcement at the wire. Claude Code's Stop hook fires after the model finishes a response and BEFORE the response is shown to the user. The hook gets the response text and the full tool-use history of the turn. It can return a blocking message that forces the model to revise the response or run a verification command.

The implementation, in pseudocode (the real file lives at scripts/hook-stop-anti-claim.js):

function stopHook(responseText, toolUseHistory) {
  const claimPattern = /\b(deployed|live|shipped|in\s+production)\b/i;
  if (!claimPattern.test(responseText)) return { allow: true };

  const hasCurl = toolUseHistory.some(call =>
    call.tool === 'Bash' &&
    /curl.*\/health/.test(call.input.command) &&
    call.output?.includes('"buildSha"')
  );
  const hasGhRun = toolUseHistory.some(call =>
    call.tool === 'Bash' &&
    /gh run (view|list)/.test(call.input.command)
  );
  if (hasCurl || hasGhRun) return { allow: true };

  return {
    allow: false,
    message: 'BLOCKED: response contains "deployed" / "live" / "shipped" / "in production" '
           + 'but no verifying curl on /health or gh run view appears in the tool-use '
           + 'history for this turn. Either run the verification command and re-respond, '
           + 'or remove the claim from your response.',
  };
}

Two non-obvious things I hit while writing this:

Word boundaries matter. The first regex I tried matched delivered as a positive case because the substring "deliver" was inside "delivered." The model started avoiding the word "delivered" in PR descriptions. Adding \b (word boundary) on both sides of the alternation fixed it.

The require.main === module idiom is a lie under strict static analysis. SonarCloud rule S3403 flags require.main === module as always-false because under strict type inference, require.main is typed in a way that prevents the equality from ever being true. The portable check is path-based:

if (path.resolve(process.argv[1] || '') === path.resolve(__filename)) {
  // Running as a script, not required as a module
}

I learned that the hard way when SonarCloud blocked the PR on the first push.

Wiring the hook

Claude Code reads hook configuration from .claude/settings.json. The Stop hook block is:

{
  "hooks": {
    "Stop": [
      {
        "matcher": "*",
        "command": "node ${CLAUDE_PROJECT_DIR}/scripts/hook-stop-anti-claim.js",
        "timeoutMs": 5000
      }
    ]
  }
}

The hook reads JSON from stdin (the response text and tool-use history), writes JSON to stdout (the allow / block decision), and exits 0. Exit code is structural — anything non-zero is treated as a hook failure and the response is shown without the hook's input.

Why this matters beyond "don't lie about deploys"

The pattern is general. Any class of false claim that an agent can make confidently — "all tests passed," "rollback successful," "the migration ran cleanly," "the customer was refunded" — has the same shape:

  1. The claim is a string the agent emits in prose.
  2. The verifying evidence is a tool call (npm test, kubectl rollout status, psql -c "select count(*) ...", stripe refunds retrieve).
  3. The agent can emit the claim without making the tool call.

The Stop hook pattern lets you encode "if the agent says X, the tool-use history must contain Y" as a rule the agent physically cannot bypass. That's a different relationship to your agent than what most operators have today — it's enforceability instead of trust.
