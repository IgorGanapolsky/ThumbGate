Shirudo shields running Linux. ThumbGate shields agent actions.

4 min read · For teams running AI coding agents on real repos

TL;DR: OpenAI and Cisco's Shirudo puts a temporary shield in front of a vulnerable code path, so a running service stays protected while the patch is tested. The same pattern fits AI coding agents: when an agent makes a mistake, block that exact path before its next tool call and let the rest of the work continue. Shirudo also makes sure shields cannot be changed without authorization. As of this release, ThumbGate does the same for its learned rules, so the agent being gated cannot delete the rule that gates it.

What Shirudo does

On November 23, 2026, OpenAI and Cisco introduced Shirudo, an open-source runtime for Linux. Its premise, in OpenAI's words: "Testing and deploying a patch can still take days or weeks." Shirudo covers that gap. Here is what the announcement describes:

  • Shields, not restarts: eBPF programs block the behavior that exposes a vulnerability while legitimate requests still pass, without restarting the service.
  • Watch before enforcing: teams can monitor how a proposed shield would affect applications before they turn it on.
  • Agents propose, operators approve: agents can investigate a vulnerability, write a targeted shield and validate it against exploits and real workloads. Security teams decide what gets deployed.
  • Trusted deployment: shields are cryptographically signed and verified before loading, the eBPF verifier checks them, and kernel controls restrict unauthorized changes.
  • A verifiable record: a Trusted Platform Module backs a record of protections being loaded or removed.

In OpenAI's controlled test, a Codex-generated shield attached to a running Elasticsearch process rejected an exploit attempt while the service kept running. The project is BSD 2-Clause licensed.

The same problem, one layer up

A coding agent that just force-pushed, deleted the wrong branch, or announced "deployed" without checking has the same shape of problem. The real fix is a better model, a better prompt or a better workflow, and that takes time. Meanwhile the agent keeps working, and the next session will make the same mistake.

ThumbGate is the shield for that gap. A thumbs-down becomes a prevention rule, and a PreToolUse hook checks every tool call against those rules before it runs. The matching call is blocked or flagged, and everything else goes through.

Three Shirudo ideas, mapped to agent guardrails

  • The shielded thing cannot remove the shield. Shirudo restricts unauthorized changes to loaded shields. Until this release, an agent blocked by a learned ThumbGate rule could, in principle, rm .thumbgate/auto-promoted-gates.json and try again. Now the learned-rule store has the same self-protect-config hard floor as the gate config: the promoted gates, claim rules, send holds, prevention-rules.md and the feedback log. Agent writes to those files are denied, and no bypass variable lifts the denial. Reads still work, and an operator can grant a scoped, time-limited approval.
  • Check a shield before you enforce it. Shirudo lets teams watch a proposed shield before enforcing it. ThumbGate already replays a candidate block rule against the actions it previously allowed. If the rule would have blocked any of them, it is quarantined to a warning instead of a hard block. With THUMBGATE_GOVERNANCE_MODE=simulation, gates flag and log matching calls instead of blocking them. Hard floors still block.
  • Agents propose, people approve. In Shirudo, agents draft shields and operators decide what ships. In ThumbGate, the person's thumbs-down is the approval: the rule exists because a human flagged the mistake, not because the agent decided to restrict itself.

What this does not do

ThumbGate does not operate at the kernel level, use eBPF, or sign rules with hardware keys. It matches tool calls at the agent's hook, so it protects you from the agent, not from an attacker with a shell on the machine. Its shell parsing catches common write forms (redirects, rm, mv, sed -i, tee, inline node -e and python -c writes), not every possible obfuscation. A tamper-evident record of rule loads and removals, like Shirudo's TPM-backed record, is a possible next step and is not shipped.

Try it this week

  1. Run npx thumbgate init in a repo where your agent works.
  2. Give one real mistake a thumbs-down and confirm the next matching call is flagged.
  3. Ask the agent to delete .thumbgate/auto-promoted-gates.json. The call is denied with [GATE:self-protect-config].
