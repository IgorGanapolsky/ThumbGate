DXC checks the code after it is written. Who checks the agent while it writes?

4 min read · For teams whose code is increasingly written by AI agents

TL;DR: DXC's new managed service has Claude Mythos find vulnerabilities, then has people validate and prioritize them, with evidence at every step. That is the right split. ThumbGate applies it one step earlier: the coding agent proposes an action, your team's thumbs-up and thumbs-down decide what it may repeat, and every decision is logged.

What DXC shipped

On November 24, 2026, DXC Technology announced Frontier Code Assurance, a managed code security service built on Anthropic's Claude Mythos model. In DXC's words:

  • Find: the model "can find flaws traditional scanners miss."
  • Validate: findings are "validated by DXC cybersecurity specialists and ranked by business impact."
  • Prove: customers get "a prioritized remediation roadmap with auditable evidence at every step."
  • Fix: DXC then helps customers remediate and patch.

Customers can start with a single application and expand from there. DXC describes itself as a Global Premier partner in the Claude Partner Network, and runs 12 security operations centers in more than 40 countries.

The sentence worth stealing

"Claude Mythos finds the potential vulnerabilities; DXC specialists decide what to do about it." The model proposes and people decide. DXC also says the bottleneck has shifted from finding flaws to prioritizing and executing the fix.

If finding flaws is cheap and fixing them is the bottleneck, the next lever is obvious: write fewer of them. More and more code is written by coding agents, and agents repeat mistakes. The same force push, the same unreviewed dependency, the same secret pasted into a command. Each repeat is one more item on somebody's remediation roadmap.

Two checkpoints, not one

  • After the code exists (code assurance): scan the application, validate findings, rank them, build a remediation plan, patch.
  • Before the action runs (ThumbGate): the agent is about to run a tool call. Last week a thumbs-down on the same pattern became a prevention rule. ThumbGate warns, or blocks in strict mode, before the call fires.

These do not compete. Code assurance shrinks the backlog of flaws you already have. A pre-action gate shrinks how many new ones an agent can add, using what your team has already learned the hard way.

The same split, at the agent

ThumbGate keeps the model-proposes, people-decide rule, but the people are your own developers, and the decision happens in the moment:

  1. The coding agent proposes an action: a shell command, a file edit, an MCP tool call.
  2. ThumbGate checks it against prevention rules learned from your team's thumbs-down feedback.
  3. A known-bad action is warned on or blocked before it runs. Everything else goes through.
  4. Each allow, warn and block is written to a local audit log. npx thumbgate inventory summarizes it: decisions per tool, the gates that blocked most, activity per day, and the false-block rate.

That last step is the "auditable evidence" idea applied to agent behavior. A reviewer can see what the agent tried, what was stopped, and how often a block was later overridden.

Start with one repo

DXC's adoption path is one application first, then expand. That is also the sensible way to roll out a gate:

  1. Run npx thumbgate init in the repository where an agent mistake would hurt most.
  2. Give the next bad agent action a thumbs-down.
  3. After a few weeks, run npx thumbgate inventory and decide whether to add more repos.
