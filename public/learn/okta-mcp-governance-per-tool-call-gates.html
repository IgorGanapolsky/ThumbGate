Okta governs the MCP connection. Who gates the tool call?

4 min read · For teams rolling out MCP servers to coding agents

TL;DR: Okta for AI Agents now registers agents and puts MCP servers behind one authorization policy. That answers "which agent may reach which server." It does not answer "should this exact tool call, with these arguments, run right now." That second question is where repeated agent mistakes happen, and it is the layer ThumbGate gates.

What Okta shipped

Okta's latest Okta for AI Agents release focuses on two questions: where are my agents and what can they do. In plain terms:

  • One registry: agent import from more builder platforms, including Cursor, Snowflake, Databricks, Workato, and Tines.
  • No hand-managed secrets: agents register through a Client ID Metadata Document, so credentials rotate without a calendar reminder.
  • Faster MCP setup: an MCP Server Catalog, plus Dynamic Client Registration for custom servers.
  • One policy: several custom MCP servers behind a single authorization server, each with its own audience and scopes, and tokens that record which user and agent were involved.

That is a real step forward. Agent identity and connection governance have been scattered one-off projects, and Okta is collapsing them into the identity layer.

The question in the comments

Under Okta's announcement post, a practitioner asked the sharpest question: the MCP server usually holds a service account with more scope than any single tool call needs, so does the policy scope per tool, or is it still one grant per server?

That is the right question. A token's scopes decide what an agent may reach. They do not look at what the agent is about to do: the tool name, the arguments, the target branch, the row count, the recipient. Okta lists "What are they doing?" and "How do I respond?" as its next two questions. A pre-action gate is one practical answer to both, today, at the developer's machine.

Connection grant vs. call gate

  • Identity layer (Okta): Is this a registered agent? Who owns it? May it reach the GitHub MCP server? Which scopes does its token carry? Kill switch when something goes wrong.
  • Pre-action layer (ThumbGate): This agent is about to call delete_branch on main. Last week a thumbs-down on the same pattern became a prevention rule. Warn, or block in strict mode, before the call fires.

The two layers do not compete. Identity narrows the blast radius to what an agent is allowed to touch. The gate narrows it again to what this agent should do right now, using what your team has already learned the hard way.

Why learned rules matter here

Per-tool policy written up front misses the mistakes nobody predicted. ThumbGate turns each thumbs-down into a prevention rule that matches on the tool and its arguments, so the second occurrence of a mistake is stopped instead of repeated. That covers MCP tool calls, shell commands, file edits, and deploys through the same pre-action hook.

Try it this week

  1. Pick one MCP tool your coding agent can reach that has burned you once: a force push, a bulk update, a post sent without review.
  2. Give that call a thumbs-down, or write the rule directly.
  3. Run the workflow again and confirm the call is flagged, or blocked in strict mode, before it reaches the server.
