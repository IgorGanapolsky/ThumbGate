Identity-aware enforcement · Tool-call boundary

The AI-agent policy vault is the new last-mile control. ThumbGate covers six of the eight prescriptions deterministically.

The emerging architecture for AI agent governance has settled on one shape: a policy-aware vault sits between agents and legacy systems, enforces identity / context / delegation, mints short-lived credentials, logs telemetry, and constrains tool-chain composition. The canonical playbook has eight prescriptions. ThumbGate covers six at the tool-call boundary today. The other two — short-lived credential minting and an HSM-backed credential broker — are out of scope. We say so honestly so the buyer knows what they get and what they still need to source elsewhere.

The eight prescriptions, mapped to ThumbGate's surface area

PrescriptionCoverageHow ThumbGate does it
1. Map the last-mile surface
Inventory every tool, API, DB, queue an agent can call.		 Covered bench/thumbgate-bench.json already classifies tool calls by service (github, sqlite, filesystem, npm, railway, shell, git). Each adapter (adapters/claude, adapters/cursor, adapters/codex, adapters/gemini, adapters/amp, adapters/cline, adapters/opencode) inventories the runtime's tool surface explicitly.
2. Identity, context, delegation explicit
User id, agent id, delegation id, session context on every call.		 Covered Every PreToolUse hook sees the full request envelope: visitorId, sessionId, installId, acquisitionId, traceId, plus the raw tool input. Telemetry preserves attribution end-to-end through checkout_bot_deflected, checkout_bootstrap, and per-step funnel events.
3. Vault / gateway in front of legacy
Agents do not call legacy directly; route through a policy-enforced layer.		 Covered The PreToolUse hook is the gateway. Every tool call is evaluated against the lesson DB before execution. The gate sits at the runtime, not at the orchestrator — the agent physically cannot bypass it once it routes through ThumbGate.
4. ABAC / PBAC policies
Subject + agent + resource + action + context decide allow / deny.		 Covered Prevention rules in config/pro/prevention-rules-pro.md + the lesson DB are the policy store. Each rule carries a matcher (tool name, file path, command pattern) and a deny reason the agent receives in its trace. Self-protection rules deny the agent's own attempts to modify ThumbGate.
5. Replace shared keys with short-lived credentials
Mint scoped, ephemeral creds; rotate continuously.		 Out of scope Honest boundary: ThumbGate does not mint credentials. That is the job of HashiCorp Vault, AWS STS, GCP STS, or a comparable credential broker. ThumbGate consumes the identity context produced by that layer; we do not replace it. The vault-layer playbook needs both: a credential broker, and an enforcement layer like ThumbGate at the tool-call boundary.
6. Telemetry + feedback loops
Log every decision; tighten policies based on what fires.		 Covered Append-only audit trail: every check decision (block / approve / log) is recorded with timestamp, tool call, matched check ID, severity, and human override status. The feedback loop is the product: a 👎 on an agent action distills into a prevention rule, which becomes a pre-action check, which prevents the next repeat. Per-step DPO/KTO export at npm run feedback:export:dpo.
7. Constrain tool chaining
Enforce allowed sequences; require approval for sensitive chains.		 Partial Per-call enforcement is deterministic and complete. Chain-level enforcement — “read_invoice → update_payment_method requires fresh user approval” — exists in the Team-tier approval-boundary feature and the Workflow Hardening Sprint pattern, but is not auto-derived from a tool graph. This is on the roadmap. For now, chains are gated by per-call rules and by Team-tier approval boundaries on irreversible actions.
8. Threat model the agent as a potential attacker
Rogue agent, prompt injection, overbroad permissions.		 Covered Four self-protection checks deny the governed agent from disabling ThumbGate, modifying check rules, killing governance processes, or overriding enforcement env vars. Compliance mapping carries NIST SP800-53, SOC2, OWASP Top 10, and CWE tags on 13 check rules. A compromised or prompt-injected agent cannot disable its own guardrails — that is the canonical “rogue agent” defense.

Where this leaves the architecture diagram

Credential broker (e.g., HashiCorp Vault, AWS STS)

Mints short-lived credentials with narrow scope and short TTL. Owns the long-lived secrets that ThumbGate does not hold.

ThumbGate PreToolUse hook

Decides allow / deny per tool call against the policy store. Logs the decision. Deterministic, replay-safe, audit-ready. Sits between the agent runtime and the credential broker's resulting API call.

Legacy system

The thing that should not be reachable from an agent without both a policy check (ThumbGate) and a short-lived credential (broker). Together they form the deterministic last-mile.

Why deterministic at the tool-call boundary, not at the prompt

Model-level safety controls are statistical. They produce a residual error rate, which (as analysts in The New Stack's Remy coverage note) translates directly into incident exposure when the agent runs continuously. Prompt-side filters can be bypassed by prompt injection. The tool-call boundary is the last point where the runtime owns the decision — the agent has chosen what to do, but the call has not yet executed. That is where deterministic, attribute-based, allow-list / deny-list enforcement actually lives.

How to start

  1. Inventory. Run npx thumbgate native-messaging-audit to surface local agent connectors. Open npx thumbgate background-governance to see which agents are running, with what blast radius.
  2. Wire the gateway. npx thumbgate init installs PreToolUse hooks for the agent runtime in use. After this, every tool call routes through the policy store. No agent code changes required.
  3. Promote one repeated failure to a rule. Thumbs-down a real mistake; ThumbGate distills it into a Pre-Action Check. The next attempt is blocked at the boundary. Repeat for every “dangerous operation” identified in step 1.
  4. Run the Workflow Hardening Sprint. For approval boundaries, org-wide rule library, shared lesson DB across team seats, and audit-ready evidence — the path from local proof to managed rollout.
