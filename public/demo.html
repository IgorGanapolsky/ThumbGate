See a thumbs-down become a gate.

Your AI coding agent makes a mistake once. ThumbGate makes sure it doesn't make it twice. Every terminal output on this page is real ThumbGate output, copied from the CLI.

  • Blocks the worst commands out of the box: force-push, rm -rf on home or root, DROP TABLE, secret leaks.
  • Learns from you: one thumbs-down stops the agent from retrying a mistake. Two make it a hard rule.
  • Runs before the action: in Claude Code, Codex and Gemini CLI it checks each tool call in the agent's pre-tool hook, on your machine, before anything executes.
Chapter 1 of 5

Install in the project where your agent works.

init finds your agent and wires ThumbGate in. Claude Code, Codex and Gemini CLI get a hard pre-tool hook, and Cursor gets one for shell commands. Cline, OpenCode and other MCP agents get the checks as an advisory gate_check tool the model can skip, so the blocks below are guaranteed only where a hook is installed. doctor confirms the wiring and prints Overall: READY.

No account, no API key and no cloud service are needed for the checks. They run on your machine.

Chapter 2 of 5

Your agent tries to force-push. It never runs.

Before each tool call, the agent's hook hands ThumbGate the proposed command. A built-in gate matches git push --force and answers deny. The agent gets the reason, and the push never happens.

This is the whole idea: the check happens before the action, not in a review afterwards.

Try it yourself without risking anything. This feeds ThumbGate the same input the hook would, without running the push:

PreToolUse hook · gate-check
echo '{"tool_name":"Bash","tool_input":{"command":"git push --force"}}' | npx thumbgate gate-check

Chapter 3 of 5

Your agent seeds production. One thumbs-down stops the retry.

No built-in rule knows that npm run db:seed -- --prod is bad in your project. You do. Type a thumbs-down in the agent session right after it runs.

ThumbGate holds that command at once: the agent's next try is denied until you say "go ahead" or give a thumbs-up. Other commands keep working, and the agent is told to ask you what to change.

Your thumbs-down is also saved as a lesson. After you release the hold, the next run of that command warns before it runs and shows the agent your lesson.

One sentence from you. No YAML, no policy file to write.

Claude Code session · your-project
# you type in the session, right after the seed ran:
> thumbs down: that seeded test rows into production
ThumbGate hold: thumbs-down received. `npm run db:seed …` is refused until the person says "go ahead". Ask what to change.

# the agent tries again:
"permissionDecision": "deny"
[GATE:thumbs-down-hold] The person gave a thumbs-down right after `npm run db:seed …`. That action is held until the person says to go on (a thumbs-up or "go ahead"). Do not retry it or route around it with another tool; ask what to change.

# after you say "go ahead", the next run warns first:
[GATE:auto-npm-run-db-seed-prod-…] WARNING: Auto-promoted repeated executable action: "npm run db:seed -- --prod" (1 occurrences in 30 days)
Chapter 4 of 5

It happens again. Two thumbs-downs make it a hard rule.

A second thumbs-down from you on the same command turns the warning into a block. Saying "go ahead" lifts the hold but not the rule: from then on the agent gets deny for that command, the same answer as a built-in gate, and it does not run.

The rule is scoped to this project, so a thumbs-down in one repo doesn't block anything in another.
