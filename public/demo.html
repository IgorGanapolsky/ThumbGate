See a thumbs-down become a gate.

Your AI coding agent makes a mistake once. ThumbGate makes sure it doesn't make it twice. Every terminal output on this page is real ThumbGate output, copied from the CLI.

  • Blocks the worst commands out of the box: force-push, rm -rf on home or root, DROP TABLE, secret leaks.
  • Learns from you: one thumbs-down on a command makes the next attempt warn. A second one blocks it.
  • Runs before the action: it checks each tool call in your agent's hook, on your machine, before anything executes.
Chapter 1 of 5

Install in the project where your agent works.

init finds your agent (Claude Code, Cursor, Codex, Gemini CLI and other MCP agents) and wires ThumbGate into its pre-tool hook. doctor confirms the hooks are really wired and prints Overall: READY.

No account, no API key and no cloud service are needed for the checks. They run on your machine.

your-project
npx thumbgate init
# detects your agent and installs the hooks

npx thumbgate doctor
# checks the hooks are wired; exits 0 when ready
Overall: READY
Chapter 2 of 5

Your agent tries to force-push. It never runs.

Before each tool call, the agent's hook hands ThumbGate the proposed command. A built-in gate matches git push --force and answers deny. The agent gets the reason, and the push never happens.

This is the whole idea: the check happens before the action, not in a review afterwards.

Try it yourself without risking anything. This feeds ThumbGate the same input the hook would, without running the push:

PreToolUse hook · gate-check
echo '{"tool_name":"Bash","tool_input":{"command":"git push --force"}}' | npx thumbgate gate-check
{"hookSpecificOutput":{
  "hookEventName": "PreToolUse",
  "permissionDecision": "deny",
  "permissionDecisionReason":
    "[GATE:force-push] Force push blocked. This is destructive and irreversible.
      Reasoning:
      • Pattern /git\s+push\s+(--force|-f)/ matched "git push --force"
      • Gate force-push [block] — layer: Execution, severity: critical
      • Manual policy rule (default.json)"
}}
Chapter 3 of 5

Your agent seeds production. You give it a thumbs-down.

No built-in rule knows that npm run db:seed -- --prod is bad in your project. You do. Type a thumbs-down in the agent session right after the command, or capture it from the CLI as shown here.

The next time the agent proposes that command, ThumbGate turns it into a check that warns before it runs, and puts your lesson in front of the agent.

One sentence from you. No YAML, no policy file to write.

your-project
npx thumbgate capture --feedback=down --context="npm run db:seed -- --prod" --what-went-wrong="seeded test rows into the production database" --what-to-change="never seed production"
Feedback Captured [DOWN]
  Signal      : negative (store-mistake)
  Storage     : JSONL log + LanceDB vector index

# later, the agent proposes the same command again:
[GATE:auto-npm-run-db-seed-prod-…] WARNING: Auto-promoted repeated executable action: "npm run db:seed -- --prod" (1 occurrences in 30 days)
  • Gate auto-npm-run-db-seed-prod-… [warn] — layer: Execution, severity: medium
  • Auto-promoted from feedback after 1 failures
[ThumbGate] Past mistakes relevant to this action — read before proceeding:
  • seeded test rows into the production database
    → never seed production
Chapter 4 of 5

It happens again. Second thumbs-down. Now it's blocked.

A second thumbs-down from you on the same command upgrades the check from warn to block. From then on the agent gets deny, the same answer as a built-in gate, and the command does not run.

The gate is scoped to this project, so a thumbs-down in one repo doesn't block anything in another.
