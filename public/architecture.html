System architecture

What each layer is for

User / agent

Why it exists: turns an intent into proposed tool calls.

What can fail: ambiguous scope, hallucinated facts, or a risky action.

How we know: the request, normalized action, and outcome receipt are linked in the audit trail.

Planner / tool router

Why it exists: chooses a bounded workflow and the least-powerful suitable tool.

What can fail: excessive fan-out, wrong tool, budget drift, or a retry loop.

How we know: scope, checkpoints, tool choice, action count, and budget are deterministic fields.

MCP / API adapters

Why it exists: gives every client one versioned contract instead of bespoke integration logic.

What can fail: schema drift, auth failure, timeout, or an over-privileged tool.

How we know: adapter contract tests, capability profiles, and per-call status receipts.

Enterprise systems

Why it exists: performs the real read or mutation in GitHub, CI, data, billing, and internal services.

What can fail: partial writes, stale reads, provider errors, or permission changes.

How we know: provider-visible receipts and post-action readback, never the agent claim alone.

Evaluator

Why it exists: compares behavior with golden cases and evidence-backed acceptance checks.

What can fail: vacuous tests, skewed samples, evaluator gaming, or silent regression.

How we know: held-out metrics, replay stability, false-block rate, and published scorecard artifacts.

ThumbGate policies

Why it exists: converts risk and workflow constraints into an effective allow, warn, approval, or deny outcome.

What can fail: evasion, over-blocking, fail-open hooks, or confusing a raw match with an actual block.

How we know: raw policy decision and effective execution disposition are stored separately and exercised by adversarial tests.

Human escalation

Why it exists: keeps consequential, ambiguous, or authority-expanding actions with an accountable reviewer.

What can fail: no approver, stale approval, or approval for the wrong action.

How we know: identity-bound, action-bound, expiring approval evidence; autonomous runs fail closed.

Why it is built this way

Deterministic orchestration around agents

Models propose; code owns scope, sequencing, permissions, budgets, retries, and terminal states. The same input can be replayed and audited without asking another model to reinterpret policy.

MCP instead of direct integrations

One typed protocol supports multiple agents, capability profiles, and local or hosted transports. Provider-specific logic stays behind adapters, so auth and schema changes do not leak into every client.

Cost control

Regex, schemas, cached local retrieval, and hard floors run before optional model calls. Workflows carry action, time, and model budgets; repeated or low-value calls are stopped before spend compounds.

Failure recovery

Operations are checkpointed and receipts are idempotent. Retryable transport failures use bounded backoff; ambiguous writes fail closed and require provider readback before resuming.

Loop limits

Every workflow has a maximum action count, retry count, elapsed-time budget, and explicit terminal states. Repeated action fingerprints and no-progress checks stop circular plans.

Append-only evidence model

Feedback, lessons, policy verdicts, effective outcomes, approvals, and receipts remain separate linked records. That preserves provenance, supports replay, and avoids rewriting history when policy changes.
